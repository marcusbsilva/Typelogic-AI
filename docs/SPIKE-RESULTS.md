## Gates

- **G1 pass:** the GGUF specialist (Q8_0) picks the PyTorch answer on 100% of JevBench, 99.2% of test2 and 99.9% of
  BANKING77 questions. On the 195 JevBench items both can read, both score 74.4%.
- **G2 fail:** Q4_K_M loses 1.1 points on test2 and disagrees with PyTorch on 7.7% of JevBench questions.
- **G3 pass:** Plumb Q4_K_M equals Q8_0 (87.9% / 86.0%).
- **G4 fail:** Clef-Flash is below Plumb on JevBench (skill 0.70 vs 0.82); above it on test2 (0.83 vs 0.79), where it
  was the main teacher of the specialist's training targets (weight 0.6), so test2 favours it.

## Decision

- Default models: **specialist Q8_0 + Plumb Q4_K_M**, routed as in 1.x (<= 16 options -> Plumb, more -> specialist):
  about 4.4 GiB on disk, both loaded at once in about 4.4 GiB of the B580 with the patched llama.dll and the router
  settings (6.2 GiB with default settings).
- Clef-Flash becomes an optional download, as the bartowski **IQ4_XS** file (5.0 GiB): with Plumb it gives the best
  probabilities, and the three models then run at once on the B580 (see below).
- The 1.x numbers are reproduced by the new path: Plumb 87.9% here vs 88.7% through Ollama in 1.x (top-64 instead of
  top-20 log-probabilities), specialist 74.4% on the readable JevBench items in both.

## Three models at once (`spike/trio.py`, 2026-10-29)

The three models loaded in one GPU with the router settings (LM-head patch, output matrix in system memory, Plumb
with 1 slot, 8192-token context and 8-bit KV cache). Every suite answered by its model while the other two stay loaded,
then 60 test2 records sent to the three servers at the same time. Each model is compared question by question with
the same model measured alone.

| Clef-Flash file | GPU memory clef + specialist + Plumb | Free | JevBench / test2 / BANKING77 (alone: 81.0 / 88.3 / 93.9) | Result |
|---|---|---|---|---|
| **bartowski IQ4_XS (5.0 GiB)** | **5,831 + 2,084 + 2,378 = 10,293 MiB** | **~1,128 MiB** | **81.8 / 88.3 / 93.8** | **all checks pass** |
| bartowski Q4_K_M (5.6 GiB) | 6,408 + 2,084 + 2,378 = 10,870 MiB | ~551 MiB | 80.5 / 87.8 / 93.7 | pass, little margin |
| ggml-org Q4_K_M (6.3 GiB) | 7,068 + 2,084 + 2,378 = 11,530 MiB | -109 MiB | 81.0 / 88.3 / 93.9 | memory fail: Windows moves the excess to system memory |

- **Specialist:** 0 changed answers on all 1,846 questions (largest probability difference 0), same latency.
- **Plumb:** 87.9% / 85.9% vs 87.9% / 86.0% alone (1 changed answer of 615 on test2, from the 8-bit KV cache); median
  latency JevBench 0.361 vs 0.314 s, test2 1.366 vs 1.944 s (the shared evidence of a request is read once).
- **Concurrent stress:** 60 records to the three servers at once in 125 s, no error, every server alive.
- With IQ4_XS, the Clef-Flash answers differ from the ggml-org file on 1-4% of questions with no net loss; its
  probabilities move more (largest difference 0.66), so calibration of the Clef x Plumb combination is checked again in
  phase 1.

## Phase 1: TypeLogic.exe against the models alone (`spike\run-spikes.bat app`, 2026-10-29)

`TypeLogic.exe` built with cargo, installed in `dist\` by `TypeLogic setup` (every file SHA-256 checked, hard links),
then the suites sent to `POST /api/evaluate` and compared question by question with the trio runs (same settings).

| Engine through TypeLogic.exe | JevBench | test2 | BANKING77 | Changed answers | Largest probability difference | Median latency added |
|---|---|---|---|---|---|---|
| specialist (forced) | 68.0% | 79.3% | 92.5% | 0 of 1,846 | 0 | +18 ms |
| Clef-Flash IQ4_XS (forced) | 81.8% | 88.3% | 93.8% | 0 of 1,846 | 0 | +15-20 ms |
| Plumb (Rust readout, forced) | 87.9% | 85.9% | - | 1 of 846 | 0.07 | +35 ms |
| automatic routing (default start) | 87.9% | 85.9% | - | 1 of 846 | 0.07 | +40 ms |

- The specialist and Clef-Flash give bit-identical answers. Plumb's prompts are byte-identical to 1.x and their token
  ids identical to the Hugging Face tokenizer (408 prompts); the remaining difference (one test2 answer, probabilities
  up to 0.07) comes from llama-server reusing cached recurrent state between prompts, as between two trio runs.
- Default start on the B580 (11.4 GiB free): Plumb + Clef-Flash, ready in 12-15 s; the three models together also
  start once the router's own memory admission is off.
- The API refuses connections on the computer's network addresses; no llama-server is left after TypeLogic.exe stops
  or is killed (Windows job object).

## Findings to act on

- **Memory of decision models (fixed by our patch):** in decision mode the release llama.cpp computes the logits of the
  whole vocabulary (248k) for every prompt token. `spike/patches/qwen35-skip-lm-head.patch` (6 lines, the rule llama.cpp
  already applies to LFM2) skips the LM head in that mode. Measured on the B580 with the specialist Q8_0: answers
  bit-identical on all 1,846 questions (largest probability difference 0, no changed answer); GPU memory 5,581 -> 2,671
  MiB (compute buffer 3,438 -> 528 MiB); median latency JevBench 0.059 -> 0.045 s, test2 0.415 -> 0.254 s, BANKING77
  0.488 -> 0.295 s, now faster than PyTorch everywhere (0.143 / 0.273 / 0.334 s). Next: propose it upstream; until it
  is in a llama.cpp release, v2 ships the patched llama.dll (MIT) next to the release binaries.
- **Long states:** the GGUF answers states over 2048 tokens (1.x refused them), but the specialist was trained up to
  1024 tokens and gets 33% of those 36 items right (Clef-Flash 67%). Phase 1 keeps a state limit for the specialist
  and sends longer states to Plumb.
- **Possible benchmark familiarity:** Plumb descends from a Jev-family model, so JevBench may favour it; test2 (our own
  held-out set) is the fairer comparison between Plumb and Clef-Flash.
